# Синхронизация базы знаний Битрикс24

Рабочий серверный компонент проекта. Получает PDF из выбранных папок Диска, Markdown-статьи из выбранных коллекций Базы знаний 2.0 и HTML-блоки выбранных баз прежнего формата. Обрабатывает уведомления и регулярно сверяет источники. На портале компании подключены четыре базы прежнего формата; разрешено чтение последних сохранённых версий независимо от публикации в Битриксе.

## Что уже реализовано

- Рекурсивный обход папок Диска, пагинация и загрузка PDF через REST API.
- Чтение дерева и текста статей Базы знаний 2.0 через REST 3.0 (`/rest/api/`).
- База знаний 1.0: источники `landing` с ID базы, чтение страниц и HTML-блоков через `scope: KNOWLEDGE`, сверка полноты и статуса публикации. Текст извлекается локально; скрипты, меню и служебные блоки не исполняются и не индексируются. Таблицы сохраняют разделители ячеек.
- `landing_read_drafts: true` читает последние сохранённые версии 1.0, включая неопубликованные страницы и правки опубликованных страниц. Публикация в Битриксе не требуется. При `require_review: true` новая версия всё равно ждёт проверки своего отпечатка. По умолчанию `landing_read_drafts: false`: неопубликованные версии сохраняются только для диагностики (`upstream_unpublished`), и полностью неопубликованный источник блокируется.
- Приём исходящих вебхуков с проверкой токена и домена портала.
- Устойчивая к перезапуску очередь в SQLite; повтор после ошибки и периодическая сверка.
- Извлечение текста PDF с сохранением номера страницы, ограничением размера и времени обработки.
- Повторная обработка изменившихся PDF; неизменившиеся файлы не скачиваются заново.
- Атомарная замена версии источника и удаление исчезнувших документов из поиска после полного успешного обхода.
- Недоступный, неполный или слишком давно проверенный источник не участвует в поиске. Старые данные остаются для диагностики.
- Проверка конкретной версии документа перед публикацией; можно включить автоматическую публикацию для заранее утверждённых источников.
- Внутренний поиск по словам с фрагментами, версией и страницей; ссылки на файлы Диска берутся из Битрикса.
- Запрет работы нескольких процессов с одной базой; база привязана к порталу и пользователю интеграции.

## Границы текущего компонента

Рабочий сайт имеет поиск и генерацию ответов через существующий локальный API Hermes. При `answers_from_sources_only: true` фактические ответы используют только подключённые материалы со ссылками; интернет-поиск отключён. Помощник учитывает контекст последних реплик, уточняет вариант инструкции и сообщает, каких сведений не нашёл. Уточняющий вопрос не требует ссылки; утверждения об инструкциях требуют её. Перед поиском локальная модель переводит вопрос на русский и восстанавливает предмет уточнения из контекста. Поиск документов остаётся лексическим, с расширением терминов зарплаты, без векторного индекса. OCR не реализован.

По запросу владельца подготовлен режим `web_public_access: true`: главный экран состоит из одной голосовой кнопки и бегущей строки на разных языках, код входа не требуется. Запись через MediaRecorder отправляется на сервер, локальная модель faster-whisper определяет язык; ответ запрашивается на этом же языке. Нет ручного выбора языка, примеров вопросов и текстового поля. Одна и та же кнопка начинает и завершает запись; после паузы запись завершается автоматически, максимальное время — 40 секунд. Сервер принимает до 4 МБ и 45 секунд аудио; записи не сохраняются на диск. Для работы нужен HTTPS и разрешение браузера на микрофон. Автоопределение предусмотрено для русского, английского, узбекского, таджикского, казахского, армянского, азербайджанского, турецкого и китайского. Кыргызский выбранная модель отдельно не поддерживает; качество языка и речи нужно проверять на реальных записях. Автоматическая озвучка ответа в этом интерфейсе не подключена.

Вход запоминается в этом браузере на 90 дней через защищённую HttpOnly-cookie. SQLite хранит только хеш токена сессии, срок и отпечаток настроенного кода; перезапуск приложения вход не сбрасывает. Выход отзывает текущую сессию. При смене кода входа или административного ключа прежние сессии отзываются. Код не сохраняется в localStorage. Выбранный язык ответов хранится на устройстве; он имеет приоритет над языком вопроса. Ответы и уточнения переводятся локальной моделью с сохранением чисел и ссылок, документы открываются на языке оригинала. Озвучка использует доступный браузерный голос языка конкретного ответа.

Административный API и внутренний поиск предназначены **только для доверенного серверного приложения**. Сервисный токен нельзя передавать браузеру или сотрудникам; публичный прокси закрывает `/admin/*` и `/internal/*`. При `web_public_access: false` вход на сайт выполняется отдельным общим кодом; прежний код и механизм сессий сохранены. При `true` подключённые `web_scopes` доступны посетителям без входа. Персональные права сотрудников Битрикса не переносятся автоматически.

Синхронизируются только явно выбранные папки/коллекции/базы. Пока нет автоматического переноса персональных ACL Битрикса. Для 1.0 сохраняются адреса видимых изображений из HTML-блоков; фотографии процитированных статей отображаются под ответом (до 12 на ответ). Сервер загружает их только с явно разрешённых HTTPS-хостов, проверяет перенаправления, размер и формат, удаляет метаданные и отдаёт локальные JPEG-копии. Кеш ограничен 400 файлами, обновляется через 300 секунд; доступ каждый раз проверяется по текущему статусу и отпечатку статьи. Клик по источнику или фото ведёт в оригинал Битрикса. OCR фотографий и автоматическое скачивание вложений не реализованы; Word, Excel и PowerPoint с Диска не импортируются. Для 2.0 возвращаются идентификатор коллекции/документа; ссылка на страницу не выдумывается. Для 1.0 адрес берётся из `PUBLIC_URL` ответа API и проверяется: только HTTPS-страница `/knowledge/` того же портала, без параметров авторизации. Скрытые блоки и служебные страницы не считаются инструкциями. Пустые страницы получают `no_text`, страницы только с изображениями — `needs_ocr`; одобрение этих статусов запрещено. Страницы с текстом и иллюстрациями требуют проверки по оригиналу.

OCR сканов пока не подключён. PDF с пустыми страницами получают `needs_ocr`; ошибочные и слишком большие файлы не попадают в поиск. Порядок строк и столбцов сложных PDF-таблиц необходимо проверить по оригиналу. Процесс извлечения имеет тайм-аут, но лимит памяти должен обеспечивать контейнер/хост при развёртывании.

## Локальный запуск на Windows

Нужен Python 3.11 или новее. Из корня проекта:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[test]"
Copy-Item settings.example.json settings.json
```

Заполните `settings.json`:

- `portal_url`: адрес портала без `/rest/`.
- `user_id`: пользователь, создавший входящий вебхук для чтения.
- `sources`: `disk` с ID корневой папки, `note` с ID коллекции 2.0 или `landing` с ID базы 1.0. Эти пространства ID различны: ID `landing` нельзя указывать как `note`. Удалите ненужные примеры.
- `landing_read_drafts`: по умолчанию `false`. Значение `true` разрешает использовать последнюю сохранённую версию независимо от статуса публикации в Битриксе. Подключайте только материалы, согласованные для аудитории приложения.
- `download_hosts`: точные дополнительные HTTPS-хосты скачивания, если портал действительно использует CDN. По умолчанию разрешён только сам портал. Каждый переход при скачивании проверяется.
- `poll_seconds`: период сверки; по умолчанию 300 секунд плюс время обработки.
- `max_stale_seconds`: допустимый возраст последней полной успешной сверки.
- `require_review`: по умолчанию `true`. После импорта версия ждёт проверки. Для источников, где публикуются только утверждённые инструкции и качество извлечения проверено, `false` включает автоматическую публикацию извлечённого текста. Ошибки и сканы всё равно блокируются.
- `answers_from_sources_only`: по умолчанию `true`. Генератор получает найденные локальные материалы; интернет-поиск не вызывается даже при старой настройке `HERMES_WEB_SEARCH`. Модель может уточнить вопрос и без результатов. Структурированный ответ разделяет фактический текст, предмет недостающих сведений и один уточняющий вопрос. Фактический текст без допустимых ссылок отклоняется: показывается исходный фрагмент или сообщение об отсутствии сведений. Из прошлых ответов модели передаются только вопросы для уточнения; история пользователя помогает понять запрос, но не служит подтверждением фактов. Для каждого продолжения заново ищутся актуальные документы.
- `allow_short_web_access_code`: по умолчанию `false`, код входа должен иметь минимум 16 символов. Временное значение `true` по прямому запросу владельца разрешает код от 3 символов. Код по-прежнему хранится только в окружении; административный токен остаётся отдельным.
- `web_public_access`: по умолчанию `false`. Явное значение `true` открывает выбранные источники без кода и включает минимальный голосовой экран. Код и административные секреты не изменяются.
- `voice_model_path`: путь к заранее скачанной модели CTranslate2 для faster-whisper. Модель работает на CPU с int8 и восемью потоками; во время распознавания ничего не скачивается. На сервере используется постоянный каталог `data/models/whisper-turbo`, версия `Zoont/faster-whisper-large-v3-turbo-int8-ct2`, commit `8d03bef2d94576dda118069ca1da6c721d27666f`.

Для строгого режима локальный API Hermes должен возвращать список инструментов на `GET /v1/toolsets` без включённых инструментов. Перед генерацией приложение проверяет это условие; если оно нарушено или недоступно для проверки, выдаёт только исходный фрагмент документа. На этом сервере применён [патч запрета инструментов API](deploy/hermes-api-sources-only.patch) и настройка `api_server_sources_only: true` в конфигурации шлюза. После обновления Hermes патч нужно проверить и при необходимости применить повторно. Настройки инструментов остальных платформ сохранены.

В настройках окружения процесса задайте:

| Переменная | Значение |
| --- | --- |
| `BITRIX_WEBHOOK_KEY` | Секретная часть входящего вебхука Битрикса; не полный URL |
| `KNOWLEDGE_API_TOKEN` | Случайный секрет не короче 32 символов для нашего серверного API |
| `BITRIX_EVENT_TOKEN` | Токен исходящего вебхука; необязателен для сверки по расписанию |
| `KNOWLEDGE_SETTINGS` | Путь к настройкам; по умолчанию `settings.json` |

Файлы `.env` автоматически не загружаются. Для ручного ввода секретов в PowerShell 7 без показа на экране можно использовать `Read-Host -MaskInput`. Не вставляйте секреты в переписку, код или публичные ссылки. `settings.json` и каталог данных исключены из Git.

```powershell
$env:BITRIX_WEBHOOK_KEY = Read-Host 'Ключ входящего вебхука' -MaskInput
$env:KNOWLEDGE_API_TOKEN = Read-Host 'Сервисный токен' -MaskInput
$env:BITRIX_EVENT_TOKEN = Read-Host 'Токен исходящего вебхука (можно оставить пустым)' -MaskInput
.\.venv\Scripts\python.exe -m uvicorn knowledge.app:create_app --factory --host 127.0.0.1 --port 8080 --workers 1
```

На старте выполняется сверка, затем она повторяется автоматически. SQLite и индекс лежат в `data/`. Не включайте подробные HTTP-логи: URL API содержит ключ доступа.

## Настройка Битрикса

1. Создать входящий вебхук с разрешениями `disk`, `note` и/или `landing` для соответствующих источников, доступными на тарифе и версии портала, от пользователя с доступом только к согласованным материалам.
2. Указать портал, ID пользователя, ключ и выбранные источники.
3. Проверить успешное чтение в `/admin/status`.
4. Если для выбранных материалов на портале доступны подходящие события, создать исходящий вебхук на `https://ВАШ-СЕРВЕР/webhooks/bitrix`. Внести его токен в `BITRIX_EVENT_TOKEN`. Конкретные имена событий намеренно не выдуманы: нужно выбрать реально доступные на портале.
5. Если подходящих событий нет, оставить сверку по расписанию. Её наличие не зависит от вебхука.

Вебхук служит сигналом к сверке. Присланные в нём URL, идентификаторы объектов и токены OAuth не используются для чтения произвольных данных. Чтение идёт только из настроенных источников. Программная регистрация событий методом `event.bind` требует контекста приложения и здесь не выполняется.

Для получения внешних уведомлений требуется доступный Битриксу HTTPS-адрес. При размещении через обратный прокси публикуйте только `/webhooks/bitrix`, ограничьте размер запроса и частоту обращений. `/admin/*` и `/internal/*` должны оставаться внутри доверенной сети. Сейчас сервис привязывается к localhost.

## API

Административные `/admin/*` и служебные `/internal/*` маршруты требуют `Authorization: Bearer <KNOWLEDGE_API_TOKEN>`. Веб-маршруты `/api/web/*` используют сессию или явно включённый `web_public_access`; входящий обработчик уведомлений проверяет отдельный токен.

| Маршрут | Назначение |
| --- | --- |
| `GET /health` | Проверка процесса; не подтверждает синхронизацию |
| `GET /admin/status` | Состояние источников, очереди и документов |
| `POST /admin/sync` | Поставить полную сверку в очередь, ответ 202 |
| `GET /admin/documents/{scope}/{id}` | Извлечённые страницы для проверки |
| `POST /admin/documents/{scope}/{id}/approve` | Одобрить именно переданный `fingerprint` |
| `POST /internal/search` | Найти фрагменты в разрешённых вызывающему серверу источниках |
| `POST /webhooks/bitrix` | Принять уведомление JSON или form-urlencoded |

Пример запроса поиска:

```json
{"query":"оформление пропуска", "scopes":["note:456"], "limit":5}
```

Для одобрения тело: `{"fingerprint":"значение из карточки документа"}`. Изменённую после проверки версию нельзя одобрить старым отпечатком. Статус `needs_ocr` или `extraction_failed` этим действием не обходится.

Если хотя бы один запрошенный источник недоступен/просрочен, поиск отвечает 503, а не создаёт впечатление, что сведений нет. Смена версии инвалидирует ранее одобренный текст; удаление исключает его из результатов после очередной успешной сверки. Изменения прав сервисного пользователя обнаруживаются при чтении; это не мгновенная синхронизация всех пользовательских прав.

## Проверка

```powershell
python -m pytest -q
```

Тесты не обращаются к реальному Битриксу и не используют ключи компании. Проверяют обе версии API, вложенные папки/статьи, пагинацию, реальное извлечение небольшого PDF в отдельном процессе, повторный импорт, смену версии, удаление, неполный обход, защиту вебхука, ограничения загрузок, изоляцию источников, устаревание и очередь после перезапуска.

Перед эксплуатацией обязательно выполнить такие же сценарии на портале компании, подключить авторизацию сотрудников, проверить качество извлечения их PDF и настроить эксплуатацию. Наличие тестов на имитации API не является подтверждением доступа к порталу.
